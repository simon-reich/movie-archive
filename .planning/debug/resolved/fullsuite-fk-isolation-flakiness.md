## Symptoms

- **Expected behavior**: `./gradlew test` (full backend suite) passes cleanly end-to-end in CI and locally.
- **Actual behavior**: Running the entire suite fails ~97-99 tests across unrelated classes (`UserControllerTest`, `SettingsIntegrationTest`, `MovieControllerTest`, `SearchControllerTest`, `WikiReloadServiceIntegrationTest`, `EnrichmentIntegrationTest`, `IndexingIntegrationTest`, `MovieDetailControllerTest`, `DashboardControllerTest`, `WikipediaClientTest`) with a mix of Spring context load failures and `DataIntegrityViolationException`/FK-constraint violations — e.g. `bulk_import_line_user_id_fkey` blocking a `users` row delete.
- **Error messages**: `DataIntegrityViolationException` wrapping a Postgres FK violation on `bulk_import_line_user_id_fkey` when some test's cleanup/setup tries to delete a `users` row that still has `bulk_import_line` rows referencing it via `user_id`.
- **Timeline**: First documented as pre-existing tech debt in Phase 15 (`.planning/milestones/v1.1-phases/15-.../deferred-items.md`, 2026-08-28), acknowledged and deferred at v1.1 milestone close as "not fixed here — pre-existing test-infrastructure gap, out of scope". Resurfaced now (2026-08-29) because the separate `backend-ci-tests-hang` debug session's fix unblocked the hung `WikiReloadControllerTest`, letting the full suite actually run to completion in CI for the first time — which is when this pre-existing failure becomes visible again instead of being masked by the earlier hang.
- **Reproduction**: Confirmed (Phase 15 investigation) that running `BulkImportControllerTest` + `UserControllerTest` together in isolation (`./gradlew test --tests "de.moviearchive.bulkimport.BulkImportControllerTest" --tests "de.moviearchive.user.UserControllerTest"`) passes cleanly — proving this is NOT caused by any specific test's own logic, but by cross-class DB-state leakage: all test classes share one Testcontainers Postgres instance with no `@AfterAll`/class-boundary cleanup, so whichever class happens to run last before a class expecting a clean `users` table can trip the FK violation depending on JVM-determined class execution order (not the individual test's fault).

## Current Focus

- **bug_class**: Compound — two independent Bohrbugs (each deterministic given fixed conditions: FK-cascade gap fires whenever a class with bulk-import residue precedes any `userRepository.deleteAll()`; connection exhaustion fires whenever accumulated distinct Spring contexts exceed Postgres's connection ceiling), both surfaced as apparent "flakiness" only because JUnit 5's class execution order is JVM/discovery-determined and shifts across runs/environments.
- **reasoning_checkpoint** (mandatory pre-fix structured reasoning — see debugger philosophy):
  - **hypothesis**: Full-suite flakiness has two independent, freshly-confirmed causes. (A) `bulk_import_line.user_id` / `bulk_import_batch.user_id` / `movies.user_id` FKs to `users(id)` lack `ON DELETE CASCADE` (unlike every other user-owned child table), so any test class's plain `userRepository.deleteAll()` throws `DataIntegrityViolationException` whenever residual rows are left behind in the ONE shared, JVM-lifetime Testcontainers Postgres instance by a class ignorant of the bulk-import tables. (B) Every WireMock-based integration test class registers its own `dynamicPort()`, giving each a uniquely-keyed Spring context that is never torn down mid-run; their independent HikariCP pools (default max-size 10) accumulate against that SAME shared Postgres container until they exceed its default `max_connections` (100), causing `FATAL: sorry, too many clients already` → `FlywaySqlException` → Spring context load failure for whichever WireMock-based classes happen to run late in JUnit's non-deterministic class order.
  - **confirming_evidence**:
    - Direct code inspection: V9/V10 migrations create `bulk_import_line.user_id`/`bulk_import_batch.user_id` with plain `REFERENCES users(id)`, no `ON DELETE CASCADE`, vs V3/V5's explicit `ON DELETE CASCADE` on every token table and `user_api_keys`; V6 shows `movies.user_id` has the same gap.
    - Fresh `./gradlew test --continue` run (2026-08-31, `DOCKER_HOST` fixed) shows literal `org.postgresql.util.PSQLException: FATAL: sorry, too many clients already` inside a `FlywaySqlException` inside a Spring `BeanCreationException` for `BulkImportControllerTest` and `WikiReloadControllerTest`'s first test methods, with 10 distinct `HikariPool-N` instances all shut down together only at JVM exit — direct proof of accumulated, never-recycled connection pools against the one shared container.
    - `TestSetupController` (production `/test/setup` endpoint, `@Profile("test")`) already manually pre-deletes `movieRepository`/`apiKeyRepository` rows before `userRepository.delete(u)` but NOT `bulk_import_line`/`bulk_import_batch` — proving the missing-CASCADE gap is a real schema defect independent of test-class ordering, not merely a test-hygiene artifact.
  - **falsification_test**: If cause A were false, adding `ON DELETE CASCADE` to the three FKs would not eliminate a reproduced `DataIntegrityViolationException` when running `BulkImportControllerTest` immediately followed by any class doing `userRepository.deleteAll()`. If cause B were false, reducing Hikari's `maximum-pool-size` for the test profile would not eliminate the "too many clients" `PSQLException` on a fresh full-suite run.
  - **fix_rationale**: Fix A (migration `ON DELETE CASCADE`) addresses the schema-level root cause directly — the same level every analogous user-owned table already solved this at — making the FK violation structurally impossible regardless of test-class cleanup order, and also fixes the identical latent bug in the production `TestSetupController` path. Fix B (reduced Hikari pool size, test profile only) bounds per-context connection consumption so ~12+ concurrently-cached Spring contexts sharing one Postgres container stay safely under its connection ceiling, without changing test architecture or behavior.
  - **blind_spots**: FK constraint names (`movies_user_id_fkey`, `bulk_import_batch_user_id_fkey`, `bulk_import_line_batch_id_fkey`) are assumed via Postgres's standard `{table}_{column}_fkey` auto-naming convention rather than independently queried against a live container — directly corroborated for `bulk_import_line_user_id_fkey` by the original reported error text, but not independently verified for the other three. The `AuthIntegrationTest` 429 rate-limit failures and `WikiReloadServiceIntegrationTest` cooldown-window timing failure seen in this same run are NOT root-caused here — assessed as likely-separate (intra-class Bucket4j-bucket-not-reset hygiene gap; and possibly contention-induced timing flake from cause B) but out of scope for this session.
  - **candidate_causes**: `config: bulk_import_line/bulk_import_batch/movies FK definitions missing ON DELETE CASCADE` (schema/migration); `config: no Hikari pool-size cap for the test Spring profile` + `environment: single fixed-capacity shared Postgres Testcontainers instance for the whole JVM run` (resource-limit category).
  - **and_gate**: No, for each individually — cause A alone is sufficient to crash a class-adjacency-dependent subset of the suite; cause B alone is sufficient to crash a context-count-dependent subset. Recorded together as a compound root-cause set (not a joint AND-gate) because both independently produce the umbrella symptom this session was opened to investigate, and fixing only one leaves the other's failure mode recurring on the next full-suite run.

## Resolution

- root_cause: (A) `bulk_import_line.user_id`/`bulk_import_batch.user_id`/`movies.user_id` FKs to `users(id)` lack `ON DELETE CASCADE` (migrations V6/V9/V10), unlike every other user-owned child table — causing `DataIntegrityViolationException` whenever residual rows survive a class boundary in the shared, JVM-lifetime Testcontainers Postgres instance; ALSO reproduces in production's `TestSetupController` E2E-reset endpoint.
