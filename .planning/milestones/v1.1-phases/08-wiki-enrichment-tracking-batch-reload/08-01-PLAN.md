<objective>
Establish the end-to-end wiki-reload architecture: attempt-timestamp tracking on both Wikipedia enrichment paths (the original save-flow AND the new retry path), and a working admin batch-reload endpoint that retries Wikipedia for a user's films missing wiki data. This plan is the tracer slice — the endpoint is synchronous and unpaced by design; Plan 08-02 adds cooldown-window eligibility filtering, `@Async` execution with a dedicated bounded executor, pacing between calls, and concurrency safeguards.

Purpose: Prove the full architecture (controller -> service -> repository -> WikipediaClient -> IndexingService -> Postgres/OpenSearch) works end-to-end before layering on the non-functional concerns (pacing, cooldown filtering, concurrency) that made the original 630-film incident possible.
Output: `V8` Flyway migration, `Movie.wikiLastAttemptedAt`, a fixed `EnrichmentService.enrich()`, a new `WikiReloadService`/`WikiReloadController`, and passing unit + integration tests proving the whole slice works.
</objective>

| client (browser/curl, JWT-authenticated) -> `WikiReloadController` | untrusted request crosses here; the path `userId` is attacker-controllable |
