<objective>
Give the currently-running bulk import a live, pushed progress stream (D-01/IMPORT-05):
`BulkImportService.runImport()`'s existing loop already knows `processed`/`total` — push that
out over Server-Sent Events instead of having any client poll or re-derive it from row counts
(which undercounts whenever the upload contained blank lines, per Phase 10's
`ImportLineParser`).

Purpose: IMPORT-05 requires the user to see live progress while an import runs. The app's
JWT auth is header-only (no cookie fallback), which rules out the browser's native
`EventSource` API for this endpoint (RESEARCH.md, Pitfall 1) — the frontend plan (11-04) will
consume this via `@microsoft/fetch-event-source` instead.
Output: `BulkImportProgressService` (in-memory `SseEmitter` registry with last-known-state
replay for reconnects), `runImport()` pushes progress after each line, a new ownership-checked
`GET /movies/bulk-import/{batchId}/progress` SSE endpoint.
</objective>

  <behavior>
    - register(batchId, emitter, totalLinesFallback): adds `emitter` to this batch's emitter
      list; wires `emitter.onCompletion(...)`/`emitter.onTimeout(...)` to remove itself from
      the list (prevents unbounded growth across app uptime). If a `lastKnown` state already
      exists for `batchId`, sends it immediately (reconnect / already-in-flight case). If NO
      `lastKnown` state exists — this app has a single global run-slot
      (`bulkImportExecutor` core=1/max=1, AsyncConfig.java) so an untracked batchId is, for
      all practical purposes, not currently running (finished earlier this process lifetime
      and evicted on complete, or predates this process) — synthesize and send an immediate
      `complete` event using `totalLinesFallback` for both `processed` and `total`, so a
      client visiting an already-finished batch's page is never left waiting forever.
    - publish(batchId, processed, total): stores `new ProgressState(processed, total, false)`
      as the batch's `lastKnown` state and sends a `"progress"` event to every currently
      registered emitter for that batchId.
    - complete(batchId): stores `new ProgressState(total, total, true)` (reusing the prior
      `lastKnown` total) as `lastKnown`, sends a `"complete"` event to every registered
      emitter, calls `emitter.complete()` on each, then removes the batch's emitter list AND
      its `lastKnown` entry (bounds memory growth per RESEARCH.md's Security Domain DoS row —
      a client that reconnects after this point hits the "no lastKnown state" fallback in
      `register()` above, which is correct: the batch is genuinely done).
    - send() failures: if `emitter.send(...)` throws `IOException` (client disconnected),
      catch it, remove the emitter from the registry, and do NOT call
      `emitter.completeWithError(...)` afterward (RESEARCH.md Anti-Patterns: the container's
      own `AsyncListener` machinery already handles completion once `send()` throws — a
      manual `completeWithError()` call after that risks a double-completion error).
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client -> GET /movies/bulk-import/{batchId}/progress | `batchId` is a client-supplied path variable — first endpoint in this phase where it becomes a lookup key |
| BulkImportProgressService (in-process, single instance) | No network boundary — purely in-memory state, no distributed broker (per RESEARCH.md's "Don't Hand-Roll" table: this app has no queue infrastructure and runs as a single backend instance) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-03 | Elevation of Privilege | BulkImportController.progress() | high | mitigate | `loadOwnedBatch()` ports `WikiReloadController.assertOwnership()`'s exact pattern — 403 on a `batchId` that resolves to a different owner. Covered by an explicit second-user 403 integration test (Task 2). |
| T-11-04 | Information Disclosure | SSE auth mechanism | medium | mitigate | Never accept a query-param token (`?token=...`) for this endpoint — the app's existing header-only `Authorization: Bearer` JWT scheme is unchanged; enforced by code review (no `@RequestParam` token path exists on this endpoint) and by the frontend plan (11-04) using `@microsoft/fetch-event-source`, never native `EventSource`. |
| T-11-05 | Denial of Service | BulkImportProgressService in-memory registry | low | mitigate | `emitter.onTimeout(...)`/`emitter.onCompletion(...)` always remove the emitter from the registry; `complete()` evicts the `lastKnown` entry too, bounding memory to at most the number of batches with an open connection or a very recently finished run (single-user-first scope; RESEARCH.md Security Domain). |
</threat_model>
