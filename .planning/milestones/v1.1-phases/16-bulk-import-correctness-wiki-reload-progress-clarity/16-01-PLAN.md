<objective>
Fix a pre-existing (Phase 10, commit eff92a5) data-integrity bug where re-uploading an
overlapping title/year across two different bulk-import batches silently reassigns a line's
`batch_id` from an older batch to the new one (CR-01, 15-REVIEW.md), and rework
`BulkImportService.processLine()`'s automatic TMDB matching from "filter to year-matches first,
NOT_FOUND on a single year-mismatched result" to a multi-stage algorithm that trusts a unique
title hit over year (user decision, 2026-08-29).

Purpose: each batch must stay a fully independent, accurate snapshot of the import run that
created it, and bulk-import's auto-match must save the single unambiguous TMDB result it
already found instead of discarding it over a year mismatch.
Output: batch-scoped `BulkImportLineRepository` query methods; `findExistingRow()` and the
`existingSaved` fast-path in `processLine()` both scoped by `batchId`; `processLine()`'s
matching pipeline reworked into the 4-branch algorithm (zero results / single result / exact
title+year narrowing / original-title fallback / ambiguous); the CR-01 regression proven
end-to-end via the existing `BulkImportControllerTest` integration test; full unit + integration
coverage for the new matching algorithm.
</objective>

| Boundary | Description |

| Authenticated user -> BulkImportService batch-scoped repository queries | `batchId` used in the new queries always originates server-side (from `createBatch()` at upload time, or the already ownership-checked `resolveLine()`/`loadOwnedBatch()` path) — this plan introduces no new externally-supplied `batchId` input surface |
