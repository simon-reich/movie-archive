<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser → `POST /movies/{id}/retry-wiki` | Authenticated user-supplied path param `id` (UUID) crosses into the backend; must not allow cross-user movie access |
| Backend → Wikipedia API (via existing `WikipediaClient`) | Outbound HTTP fetch, unchanged from Phase 8, now triggered by a client-initiated single action instead of only a batch |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Elevation of Privilege (IDOR) | `MovieDetailService.retryWiki` / `MovieDetailController.retryWiki` | high | mitigate | `userId` resolved from the JWT via `resolveUserId(auth)`; movie loaded via `movieRepository.findByIdAndUserId(movieId, userId)` — a movie owned by another user returns 404, never leaks existence or lets the caller trigger a retry on it (identical pattern to `getDetail`/`updatePersonal`/`deleteMovie`, covered by Task 2's ownership tests) |
| T-09-02 | Tampering | `@PathVariable UUID id` | low | mitigate | Spring's built-in UUID path-variable binding rejects a malformed `id` with 400 before the controller method runs — framework-level, no custom code needed (same as all 3 existing `@PathVariable UUID` uses in this controller) |
| T-09-03 | Denial of Service (external, against Wikipedia) | Repeated manual clicks on Retry | low | accept | Per D-01/D-02: a single human clicking one button for one movie cannot approach the ~630-simultaneous-call incident that motivated Phase 8's pacing; no rate limit is added here per the user's explicit decision that a manual click is a deliberate one-off action |
</threat_model>
