<objective>
Restructure BulkImportService's per-line enrichment dispatch into an explicit two-pass shape: first
resolve TMDB detail (and therefore imdbId) for every newly-matched line in the run, then issue one
batched SPARQL call for every collected imdbId, then enrich each matched line using the cached
results (D-03).

Purpose: BulkImportService has the exact one-movie-at-a-time exposure that caused the original
~630-movie rate-limit incident this whole milestone exists to fix — `processLine()` fires
`enrichmentService.enrich()` per matched line, and (unlike batch-reload, where `movie.imdbId` is
already persisted from a prior save) bulk-import's imdbId today is only discovered inside
`enrich()`'s own TMDB detail call, so there is currently no point before enrichment where all of a
run's imdbIds are known together. This plan front-loads that discovery so Plan 1's batching
primitive can be used the way it is designed to be used.
Output: a bulk import of N matched lines resolves Wikidata data in at most ceil(N/50) SPARQL
requests, not N.
</objective>

## Trust Boundaries

|----------|-------------|
| Async bulk-import job (internal, user-triggered via the existing bulk-import upload endpoint) -> TMDB detail endpoint (new call site added by this plan) | Same trust level and same TMDB-key-from-settings mechanism as the existing TMDB search call already made by processLine() — no new boundary is crossed, only an additional call using an already-established, already-encrypted-at-rest credential |
| Async bulk-import job -> WikipediaClient | No new external input crosses a boundary here — this plan only changes call ordering/threading of data (imdbId, resolved-title map) that Plan 1 already validates at the WikipediaClient layer |
