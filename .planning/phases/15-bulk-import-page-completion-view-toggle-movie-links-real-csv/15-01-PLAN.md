<objective>
Complete the read-only half of the bulk-import batch-detail page (`/imports/{batchId}`): a grid/list view toggle,
whole-card links from SAVED lines to their saved movie, and a visually distinct PARSE_ERROR category that shows the
original raw line text for traceability. This closes D-01 through D-07 and the display half of D-11 from
`15-CONTEXT.md`. Inline resolve for AMBIGUOUS/NOT_FOUND (D-08–D-10, the interactive half of D-11) is Plan 15-02;
real CSV parsing (D-12–D-17) is Plan 15-03 — both come later because they touch `BulkImportController.java` again
(file-overlap forces sequential waves).

Purpose: The batch-detail page currently only tells the user WHAT happened per line (Phase 11) — this plan makes
SAVED lines reachable (click through to the actual movie) and makes PARSE_ERROR lines diagnosable (see the exact
raw text that failed), directly continuing the fix started in `.planning/debug/bulk-import-not-adding-movies.md`.

Output: `BulkImportLineResult` DTO carries `id`, `movieId`, `rawLine`; `getBatchDetail()` resolves `movieId`
server-side; `[batchId].vue` renders whole-card movie links, a distinct PARSE_ERROR treatment, and a
grid/list view toggle backed by `localStorage`.
</objective>

<deviation_note>
## Known deviation risk: D-02 (localStorage) vs. this codebase's existing useCookie fix — DO NOT silently switch

`15-RESEARCH.md` found that `frontend/stores/search.ts` already solved the IDENTICAL grid/list view-mode
persistence problem for `/search`, using `useCookie` instead of `localStorage`, with an inline comment
documenting that `localStorage` was tried first and reverted because it caused an SSR hydration-mismatch flash
(Nuxt 3 runs with SSR enabled; `localStorage` doesn't exist during the server render pass).

`15-CONTEXT.md`'s D-02 explicitly locks `localStorage` for THIS page. Per context-fidelity rules, Task 2 below
implements D-02 exactly as locked — `localStorage`, guarded entirely inside `onMounted()`/a client-only watcher —
and accepts the one-frame hydration flash as a known, documented, low-severity tradeoff (this is a low-traffic
one-off batch-report page, not the main search results page, so the impact is smaller than the case `search.ts`
was originally fixing). Do NOT unilaterally switch to `useCookie` — if the flash proves visually distracting in
manual testing, that's a follow-up user decision, not something to silently resolve here.
</deviation_note>
