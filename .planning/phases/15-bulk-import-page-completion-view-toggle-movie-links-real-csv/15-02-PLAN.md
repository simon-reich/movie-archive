<objective>
Add inline ambiguous/not-found resolution to `/imports/{batchId}`: expanding an AMBIGUOUS or NOT_FOUND line runs a
fresh TMDB search prefilled with that line's title, lets the user pick the correct candidate, saves it through the
existing movie-save pipeline, AND updates that specific `BulkImportLine` row so the batch report reflects the
resolution — closing the gap the 2026-08-25 todo called out ("no way to see, back on the batch page, that a given
line has since been resolved"). Implements D-08–D-10 and confirms D-11's "no widget on PARSE_ERROR" boundary.

Purpose: `BulkImportService` never persists TMDB candidates for AMBIGUOUS lines (confirmed in code — only the
AMBIGUOUS status is upserted), so this is genuinely new server-side capability, not just new frontend UI: a fresh
search, a new save-and-link endpoint, and a widget wired to both.

Output: `BulkImportLineRepository.findByIdAndBatchId()`, `BulkImportService.resolveLine()`,
`POST .../lines/{lineId}/resolve`, `ResolveLineRequest` DTO, `useBulkImport().resolveLine()`, and an inline
search-and-pick widget on AMBIGUOUS/NOT_FOUND cards in `[batchId].vue`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated user (JWT) → POST .../lines/{lineId}/resolve | NEW endpoint, NEW path variable (lineId) not previously addressable by any client — the primary new attack surface this plan introduces |
| Request body (tmdbId, posterPath) → persisted BulkImportLine row | Client-supplied data written into a database row the batch-detail page later renders back to the same user |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-01 | Elevation of Privilege | POST /movies/bulk-import/batches/{batchId}/lines/{lineId}/resolve | high | mitigate | `loadOwnedBatch()` verifies batchId ownership; `BulkImportLineRepository.findByIdAndBatchId(lineId, batchId)` additionally verifies the lineId belongs to THAT SPECIFIC batch (not merely that it exists, and not merely that the batch is owned) — a lineId from another batch (even one owned by the same user) or another user's batch both resolve to 404/403 via the existing exception handlers. Directly tested (see Task 1 acceptance_criteria). |
| T-15-03 | Tampering | ResolveLineRequest.tmdbId | medium | mitigate | `@Positive` validation (mirrors `SaveMovieRequest`) rejects zero/negative tmdbId at the controller boundary via the existing `MethodArgumentNotValidException`-equivalent 400 path (`@Valid` + existing validation error handling already wired for `/movies/save`). |
| T-15-04 | Tampering | ResolveLineRequest.posterPath (client-supplied, not re-derived server-side) | low | accept | The authenticated user can only ever POST an arbitrary `posterPath` for a LINE THEY ALREADY OWN (per T-15-01's mitigation) — this only lets a user tamper with their own account's display data, not another user's. `posterPath` is only ever consumed via Vue's `:src` attribute binding (never `v-html`), so no DOM-based injection is possible even with an adversarial string. This mirrors the existing `saveAndUpsert()` pattern elsewhere in `BulkImportService`, which already trusts the search-result-sourced `posterPath` without a server-side re-fetch. |

</threat_model>
