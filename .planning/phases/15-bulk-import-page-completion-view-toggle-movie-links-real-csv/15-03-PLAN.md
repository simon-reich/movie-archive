<objective>
Add real comma-delimited CSV parsing (quoted fields, optional header row) as a second supported bulk-import
format, fully additive alongside the existing strict semicolon format — closing the deferred SET-06 backlog item
folded into this milestone. Implements D-12–D-17 from `15-CONTEXT.md`.

Purpose: The current bulk-import parser only accepts `Title;OriginalTitle;Year` — any real CSV export (comma
field separator, quoted fields for titles containing commas) currently misparses into PARSE_ERROR. This plan adds
a sibling parser using Apache Commons CSV, detected once per uploaded file, with zero changes to the existing
semicolon path's behavior.

Output: `ImportLineParser.parseCsv()`, file-level format detection + header-skip in `uploadBulkImport()`, format
dispatch threaded through `BulkImportService.runImport()`/`processLine()`, `commons-csv` dependency added.
</objective>

## CSV as a second supported format — add-alongside, not promote

The mechanical assumption-delta scan on this phase returned `detected: false`, but the orchestrator's planning
context explicitly flagged this as worth evaluating: CSV parsing (D-12–D-16) introduces a SECOND supported input
format alongside the existing semicolon-delimited format (D-17 requires the legacy format to keep working
unchanged) — the "second X was introduced where there was one" pluralization pattern.

**Decision: add-alongside, not promote.** The two parsers (`parse()` for semicolon, `parseCsv()` for CSV) stay as
two independent, sibling methods on `ImportLineParser`, both returning the identical `ParsedLine` record. Format
selection is a one-time, file-level boolean (`isCsvFormat`) computed in the controller from a first-line comma
sniff — NOT a first-class, user-facing "format" property stored anywhere, not a config flag, not a value in any
DTO or database column. `BulkImportLine`/`BulkImportLineResult` never record which format a line came from.

**Rationale:** D-12 explicitly frames this as "purely additive parsing capability" (reversible, per CONTEXT.md's
own rationale: "removing CSV support later wouldn't break the semicolon path"). Promoting format to a first-class
chosen/detected property would mean a schema change (a `format` column), a DTO field, and frontend surface to
show/select it — none of which any decision in D-12–D-17 asks for, and Claude's Discretion note for this area
only asks for a detection *strategy*, not a stored, user-visible property. The user-facing behavior stays
"upload your file, whichever of the two supported shapes it's in just works" — add-alongside matches that intent
exactly.
</assumption_delta_decision>
