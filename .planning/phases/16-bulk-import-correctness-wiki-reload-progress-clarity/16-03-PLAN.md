<objective>
Close UAT gap G-16-2: after a wiki-reload run ends (via Stop or a genuine finish), the per-movie history list
shows the last processed movie's row twice, in two consecutive entries.

Root cause is already confirmed (`.planning/debug/16-history-duplicate-on-stop.md`, no debugging needed): two
cooperating, individually-correct-by-design behaviors combine into one visible bug. (1) D-04's
`WikiReloadProgressService.complete()` change deliberately echoes the immediately-preceding `progress` event's
`lastMovieTitle`/`lastMovieStatus` into the terminal `complete` event — this is documented, intentional
last-known-state bookkeeping, not itself a bug, and needs no further backend change here. (2) `settings.vue`'s SSE handler
pushes a new `wikiMovieHistory` row whenever `p.lastMovieTitle` is truthy, with no check on `p.complete` — so it
pushes once for the movie's own genuine `progress` event, then a second time for the terminal `complete` event
that merely echoes the same data forward. This reproduces on ANY run that processes at least one movie, not only
a Stop-mid-run (confirmed in the debug session's Evidence).

Purpose: the per-movie history is the user's only record of what actually happened during a batch — a duplicated
final row misrepresents the real count of processed movies and erodes trust in the list.

Output: `settings.vue`'s history-push condition gains a `!p.complete` guard; `settings.spec.ts` gains regression
tests firing a realistic progress-then-complete event sequence for the same movie (both the Stop path and the
genuine-finish path) and asserting the history list's length stays at 1.
</objective>
