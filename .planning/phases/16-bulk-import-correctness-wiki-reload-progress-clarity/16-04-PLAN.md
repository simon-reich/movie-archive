<objective>
Close UAT gap G-16-3: "Artists Under the Big Top: Perplexed" (and 40 other movies in the live dataset with the
identical shape) displays a SUCCESS checkmark in the per-movie history on every wiki-reload run, yet keeps
resurfacing as eligible on every subsequent run — an internally-inconsistent experience the user reads as "it
says it worked, but it keeps trying again as if it didn't."

Root cause is already confirmed (`.planning/debug/16-notfound-icon-shows-checkmark.md`, no debugging needed):
NOT a rendering bug. Two independently-implemented, conflicting definitions of "Wikipedia data found" coexist —
(1) `MovieRepository.findEligibleForWikiReload` treats a movie as eligible until `wiki_plot IS NULL AND
wiki_critics IS NULL`, i.e. "found" means extractable Plot/Critics content exists; (2)
`WikiReloadService.WikiRetryOutcome.SUCCESS` (the value D-09's per-movie history checkmark renders verbatim)
means only that `WikipediaClient.fetch()` located a page at all, independent of whether any content section was
extracted. A movie whose real, correctly-matched Wikipedia page has no section under exactly the names
`WikipediaClient.findSectionIndex()` recognizes (`Plot` / `Critical response` / `Reception` / `Critical
reception`) satisfies definition #2 (genuinely found -> SUCCESS, checkmark) but never satisfies definition #1
(stays "eligible" -> retried forever). Confirmed live: 41/305 movies in the dataset share this exact shape
(`wiki_url` set, `wiki_plot` and `wiki_critics` both null).

Per the product decision made for this gap closure: the SIMPLEST correct fix that fully resolves the reported
symptom (retried forever despite a genuinely-found page) without new schema/state is to key retry-eligibility off
`wiki_url IS NULL` instead of `wiki_plot IS NULL AND wiki_critics IS NULL` — aligning definition #1 with
definition #2's existing, correct "a page was located" semantics. `WikipediaClient`'s fixed section-name
allowlist (why content extraction fails for these pages) is a separate, larger scope (content-extraction
quality) and is explicitly out of scope for this plan.

Purpose: stop wasting paced Wikipedia calls re-fetching pages that were already successfully located, and make
the per-movie history's SUCCESS checkmark mean what it says — found once, done, not retried again.

Output: `MovieRepository.findEligibleForWikiReload`'s WHERE clause and javadoc updated to key eligibility on
`wiki_url IS NULL`; the existing `WikiReloadServiceIntegrationTest` regression test that encoded the OLD (now
reversed) design intent is superseded with one asserting the new, correct exclusion.
</objective>
